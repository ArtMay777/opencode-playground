## 1. Вступ

### Що це за репозиторій

Це **робоче середовище**, а не готовий продукт. У ньому є:

- **Frontend** — React + TypeScript + Vite + Tailwind CSS (`apps/web`).
- **Backend** — Node.js + Express + TypeScript (`apps/api`) з одним endpoint `GET /api/version`.
- **Тести** — Vitest і React Testing Library (unit-тести), Playwright (end-to-end тести).
- **AI-середовище** — інструкції для агентів (`AGENTS.md`), конфігурація OpenCode, три спеціалізовані агенти та три slash-команди.
- **Документація** — шаблони для вимог і архітектури у папці `docs/`.

Стартова сторінка лише показує, що frontend працює і може отримати версію з backend.

### Що ви будуєте

Невеликий, але **завершений** full-stack застосунок за власною ідеєю: наприклад, трекер звичок, список покупок, журнал читання, планувальник подій. Ви самі визначаєте вимоги, приймаєте технічні рішення та перевіряєте результат.

### Чому тут немає готової функціональності

Бо найважливіші навички — саме ті, яких тут навмисно немає: сформулювати вимоги, обрати архітектуру, розбити роботу на кроки, перевірити й зрозуміти код. Стартер забирає рутинне налаштування (збірка, тести, proxy), щоб ви зосередилися на продукті й інженерних рішеннях.

### Що означає AI-assisted розробка у цьому завданні

Ви працюєте разом з AI-агентом у терміналі. Агент читає код, пропонує план, пише код, запускає тести. Але **відповідальність за результат — ваша**:

- ви вирішуєте, *що* будувати, і погоджуєте план;
- ви рухаєтеся маленькими кроками й перевіряєте кожен;
- ви читаєте згенерований код і ставите запитання, якщо щось незрозуміло;
- ви не вірите на слово фразі «усі тести пройшли» — ви бачите результат запуску.

AI — це дуже швидкий помічник, який іноді впевнено помиляється. Ваша роль — інженер, який керує роботою та перевіряє її.

## 2. Що потрібно встановити

Усе потрібне — безкоштовне. Платна підписка на AI-сервіси **не обов'язкова**.

| Програма | Навіщо | Де взяти |
| --- | --- | --- |
| **Git** | керування версіями коду | [git-scm.com/downloads](https://git-scm.com/downloads) |
| **Node.js** (разом з **npm**) | запуск JavaScript/TypeScript, встановлення пакетів | [nodejs.org/en/download](https://nodejs.org/en/download) — оберіть версію **LTS** |
| **OpenCode** | AI-агент для програмування в терміналі | [opencode.ai/docs](https://opencode.ai/docs) (детальніше в розділі 4) |
| **Редактор коду** | читати й редагувати код | наприклад, [Visual Studio Code](https://code.visualstudio.com/) або будь-який інший |
| **Обліковий запис GitHub** | щоб зробити fork і зберігати свою роботу | [github.com/signup](https://github.com/signup) |

Потрібна версія Node.js — **22.18 або новіша** (рекомендовано актуальну LTS). Перевірте, що все встановлено:

```bash
git --version
```

```bash
node --version
```

```bash
npm --version
```

> **Windows:** команди з цього README працюють у PowerShell або Git Bash. Там, де синтаксис відрізняється, наведено варіант для PowerShell.

## 3. Початок роботи

### Оригінальний репозиторій, fork і локальна копія

Важливо розрізняти три «копії» проєкту:

| Що | Де | Чиє | Для чого |
| --- | --- | --- | --- |
| **Оригінальний репозиторій** (upstream) | GitHub | викладача | шаблон для всіх студентів. Ви його **не змінюєте** |
| **Ваш fork** (origin) | GitHub, у вашому акаунті | ваш | ваша онлайн-копія. Сюди ви робите push і тут відкриваєте pull request |
| **Локальна копія** (clone) | ваш комп'ютер | ваш | тут ви та AI-агент пишете код |

```
Оригінальний репозиторій ──fork──► Ваш fork на GitHub ──clone──► Папка на вашому комп'ютері
      (викладача)                       (origin)          ◄──push──     (тут ви працюєте)
```

### Крок 1. Зробіть fork

1. Відкрийте сторінку оригінального репозиторію на GitHub (посилання дає викладач).
2. Натисніть кнопку **Fork** (праворуч угорі).
3. Залиште свій акаунт як власника і натисніть **Create fork**.

Тепер у вас є власна копія: `https://github.com/<ваш-username>/opencode-playground`.

### Крок 2. Клонуйте свій fork

Клонуйте **свій fork**, а не оригінальний репозиторій. Замініть `<ваш-username>` на ваше ім'я користувача GitHub (якщо репозиторій називається інакше, підставте його назву):

```bash
git clone https://github.com/<ваш-username>/opencode-playground.git
```

```bash
cd opencode-playground
```

### Крок 3. Встановіть залежності

Одна команда з кореня репозиторію встановлює все для frontend і backend:

```bash
npm install
```

### Крок 4. Запустіть застосунок

```bash
npm run dev
```

Ця команда запускає backend і frontend разом. У терміналі ви побачите рядки з префіксами `[api]` і `[web]`, зокрема:

```
[api] API server listening on http://localhost:3001
[web]   ➜  Local:   http://localhost:5173/
```

Не закривайте цей термінал, поки працюєте із застосунком. Зупинити сервери — `Ctrl+C`.

### Крок 5. Відкрийте frontend у браузері

Перейдіть на [http://localhost:5173](http://localhost:5173). Ви побачите сторінку «Welcome! Your workspace is ready.» і картку **Frontend — React is running**.

### Крок 6. Перевірте з'єднання з backend

На тій самій сторінці картка **Backend** має показати `Connected to api v0.1.0`. Це означає, що браузер надіслав запит до `/api/version`, Vite передав його в Express, і відповідь повернулася.

Можна перевірити backend і напряму: відкрийте [http://localhost:3001/api/version](http://localhost:3001/api/version) — ви побачите JSON:

```json
{ "name": "api", "version": "0.1.0" }
```

Якщо бачите «Cannot reach the API» — перейдіть до розділу [Troubleshooting](#8-вирішення-проблем-troubleshooting).

### Крок 7. Запустіть unit-тести

Відкрийте **другий** термінал (перший зайнятий `npm run dev`) і виконайте:

```bash
npm run test
```

Запустяться тести frontend (`apps/web/src/App.test.tsx`) і backend (`apps/api/src/server.test.ts`). Усі мають бути зелені (`passed`).

### Крок 8. Запустіть Playwright (end-to-end) тести

Playwright відкриває справжній браузер і перевіряє, що frontend показує версію з backend. Спочатку один раз завантажте браузер Chromium:

```bash
npm run test:e2e:install
```

Потім запустіть тести:

```bash
npm run test:e2e
```

Playwright сам запускає обидва сервери (або використовує вже запущений `npm run dev`). Звіт можна відкрити командою `npx playwright show-report`.

> **Linux:** якщо браузер не запускається через відсутні системні бібліотеки, виконайте `npx playwright install --with-deps chromium`.

Якщо всі вісім кроків пройшли успішно — середовище готове. 🎉

## 4. Налаштування OpenCode

> Цей проєкт використовує конфігурацію **OpenCode V2**. Якщо у вас встановлена стара версія OpenCode 1.x, видаліть її (тим самим способом, яким встановлювали) перед встановленням нової.

### 4.1. Встановлення

Актуальні команди завжди є в [офіційній документації](https://opencode.ai/docs). На момент написання:

macOS / Linux:

```bash
curl -fsSL https://opencode.ai/v2/install | bash
```

Або через npm (будь-яка ОС з Node.js):

```bash
npm install -g @opencode/cli
```

Або Homebrew (macOS): `brew install anomalyco/tap/opencode-v2`.

**Windows:** завантажте архів CLI для Windows з [opencode.ai/docs](https://opencode.ai/docs) (менеджери пакетів Windows офіційно не підтримуються) або встановіть desktop-застосунок звідти ж.

Перевірте встановлення:

```bash
opencode --version
```

### 4.2. Підключення облікового запису / провайдера

OpenCode сам по собі не містить AI-моделі — він підключається до **провайдера** (сервісу, який надає моделі).

1. Запустіть OpenCode у папці проєкту (див. 4.5) і введіть команду:
   ```text
   /connect
   ```
2. Оберіть провайдера зі списку і виконайте інструкції (вхід через браузер або вставлення API key).

**Безкоштовні моделі.** OpenCode пропонує безкоштовні моделі через власного провайдера (OpenCode Console):

1. Створіть обліковий запис на [opencode.ai/console](https://opencode.ai/console).
2. У терміналі OpenCode виконайте `/connect` і оберіть OpenCode / ваш workspace.

Умови доступу (чи достатньо безкоштовного облікового запису, ліміти, регіони) встановлює провайдер, і вони **змінюються**. Актуальну інформацію дивіться на сторінці [Free models](https://opencode.ai/docs/console/models#free-models). Якщо від вас вимагають оплату, а ви цього не хочете — не вводьте платіжні дані та зверніться до викладача: можна підключити іншого провайдера, який має безкоштовний рівень.

Можна також підключити будь-якого іншого провайдера, акаунт у якого у вас уже є.

### 4.3. Як знайти безкоштовні моделі

- Виконайте `/models` — ви побачите список моделей підключених провайдерів.
- Безкоштовні моделі OpenCode зазвичай мають **«Free»** у назві або нульову ціну в [таблиці цін](https://opencode.ai/docs/console/models).

Важливо знати:

- **Безкоштовні моделі доступні «на обмежений час».** Сьогоднішня безкоштовна модель завтра може стати платною або зникнути. Цей проєкт навмисно **не прив'язаний до конкретної моделі**.
- **Можуть бути ліміти** — наприклад, кількість запитів на день.
- **Деякі моделі недоступні в окремих країнах і регіонах.** Якщо модель не працює — оберіть іншу.
- **Політика щодо даних різна.** Деякі провайдери безкоштовних моделей зберігають запити або використовують їх для навчання. **Не надсилайте в чат паролі, ключі, персональні чи конфіденційні дані.**

### 4.4. Вибір моделі

```text
/models
```

Оберіть модель зі списку. Вибір застосовується до поточної сесії. Субагенти (frontend, backend, reviewer) автоматично використовують ту саму модель.

Порада: для планування та складних задач обирайте найсильнішу доступну модель; якщо модель часто помиляється або «губиться» — спробуйте іншу.

### 4.5. Запуск OpenCode у репозиторії

Завжди запускайте OpenCode **з кореня проєкту** — тоді він підхопить конфігурацію та інструкції:

```bash
cd opencode-playground
```

```bash
opencode
```

Корисні дії в терміналі OpenCode:

| Дія | Як |
| --- | --- |
| Переключити агента `build` ↔ `plan` | `Shift+Tab` (або `/agents`) |
| Обрати модель | `/models` |
| Нова сесія (чистий контекст) | `/new` |
| Повернутися до попередньої сесії | `/sessions` |
| Скасувати останній крок агента | `/undo` (повернути — `/redo`) |
| Прикріпити файл до запиту | `@` і почніть вводити назву файлу |
| Список усіх команд | введіть `/` або натисніть `Ctrl+P` |

### 4.6. Де лежать AI-інструкції проєкту

| Файл | Що містить |
| --- | --- |
| `AGENTS.md` | головні правила для всіх агентів: структура, конвенції, перевірки |
| `opencode.jsonc` | конфігурація OpenCode: агент за замовчуванням, дозволи, додаткові інструкції |
| `.opencode/agents/` | спеціалізовані субагенти: `frontend.md`, `backend.md`, `reviewer.md` |
| `.opencode/commands/` | slash-команди: `plan-feature.md`, `implement.md`, `verify.md` |
| `docs/requirements.md` | вимоги до **вашого** застосунку (заповнюєте ви) |
| `docs/architecture.md` | архітектурні рішення (оновлюєте ви та агенти) |

Усі ці файли — звичайний текст. Відкрийте їх і прочитайте: так ви зрозумієте, що саме «знає» агент.

## 5. Як влаштоване AI-середовище

### AGENTS.md

OpenCode автоматично додає `AGENTS.md` до контексту кожної сесії. Це «інструкція для нового члена команди»: де що лежить, як писати код, які тести додавати, які команди запускати для перевірки. Якщо агент постійно робить щось не так — додайте коротке правило сюди.

### Конфігурація OpenCode (`opencode.jsonc`)

Невеликий файл з коментарями. Він:

- обирає агента `build` за замовчуванням;
- **не** задає модель — ви обираєте її самі через `/models`;
- додає `docs/requirements.md` і `docs/architecture.md` до контексту кожного агента;
- налаштовує дозволи (див. нижче).

### Основні агенти: build і plan

Це вбудовані агенти OpenCode (primary agents), між якими ви перемикаєтеся клавішею `Shift+Tab`:

- **build** — повноцінний розробник: читає й змінює файли, запускає команди. Використовуйте для реалізації.
- **plan** — лише читає й аналізує, **не змінює файли проєкту**. Використовуйте, щоб обдумати задачу й отримати план, перш ніж писати код.

### Субагенти: frontend, backend, reviewer

Субагенти — це помічники, яким основний агент може **делегувати** частину роботи. Кожен працює в окремій сесії зі свіжим контекстом і повертає звіт.

| Субагент | Спеціалізація | Може змінювати файли? |
| --- | --- | --- |
| `frontend` | React-компоненти, Tailwind, стани завантаження/помилки, доступність, тести UI (`apps/web`) | так |
| `backend` | Express endpoints, валідація, бізнес-логіка, обробка помилок, тести API (`apps/api`) | так |
| `reviewer` | code review: баги, відсутні тести, інтеграція, відповідність вимогам, безпека | **ні** (заборонено дозволами) |

Основний агент вирішує сам, коли делегувати (за описом субагента). Ви також можете попросити прямо:

```text
Use the backend subagent to add input validation to POST /api/tasks.
```

```text
Попроси reviewer subagent переглянути мої поточні зміни.
```

### Slash-команди

| Команда | Що робить | Змінює код? |
| --- | --- | --- |
| `/plan-feature <опис>` | читає документацію, аналізує фічу, ділить роботу між frontend і backend, пропонує API, acceptance criteria, кроки та відкриті питання | ні (агент `plan`) |
| `/implement [опис або нічого]` | реалізує фічу або погоджений план з цієї сесії, додає тести, оновлює архітектуру, запускає перевірки | так |
| `/verify [на чому зосередитися]` | запускає lint, typecheck, тести, build, E2E; перевіряє відповідність вимогам; просить reviewer зробити review; звітує PASS / FAIL / NOT RUN | ні |

Команди — це звичайні Markdown-файли в `.opencode/commands/`. Відкрийте їх, щоб побачити точний текст запиту.

### Дозволи агентів (permissions)

Дозволи визначають, що агент може робити сам, а що — лише з вашого підтвердження:

| Дія | Правило |
| --- | --- |
| Читати та змінювати файли **всередині** репозиторію | дозволено |
| Будь-який доступ до файлів **поза** репозиторієм | питає вас |
| Shell-команди загалом | питає вас |
| `npm run ...`, `npm test`, `npx playwright test`, `git status/diff/log/show`, `ls`, `pwd` | дозволено |
| `git push` | **заборонено** — push робите ви самі після перевірки |
| Читання `.env` файлів (секрети) | питає вас (вбудоване правило OpenCode) |
| Агент `reviewer`: зміна файлів і будь-які команди, крім `git status/diff/log/show` | **заборонено** |

Коли агент питає дозвіл, ви бачите точну команду й можете обрати **Allow once** (один раз), **Allow always** (завжди для цього проєкту) або **Reject**. Читайте команду, перш ніж погоджуватися, і обережно з «Allow always» для небезпечних команд (наприклад, `rm`).

## 6. Створення власного застосунку

### Рекомендований процес

1. **Оберіть ідею.** Щось просте, корисне для вас і зрозуміле: 1–2 основні сутності (наприклад, «задача», «книга»), без оплат, авторизації та інтеграцій із зовнішніми сервісами.
2. **Визначте реалістичний MVP.** Мінімальна версія, якою можна скористатися від початку до кінця. 3–6 user stories — достатньо.
3. **Напишіть вимоги разом з AI.** Заповніть `docs/requirements.md` — за шаблоном, який там уже є.
4. **Попросіть агента спланувати рішення.** `/plan-feature` для першої фічі.
5. **Перегляньте й уточніть план.** Чи все зрозуміло? Чи немає зайвого? Відповідайте на відкриті питання агента.
6. **Реалізуйте маленькими кроками.** Одна фіча (або один крок плану) за раз: `/implement`.
7. **Використовуйте спеціалізованих агентів, де це доречно.** Для великих змін основний агент делегує роботу `backend` і `frontend`; дрібниці він робить сам.
8. **Запустіть перевірку.** `/verify` або `npm run verify` + `npm run test:e2e`.
9. **Перегляньте й виправте помилки.** Читайте звіт, просіть агента виправити конкретні проблеми, перевіряйте застосунок у браузері самі.
10. **Закомітьте завершену роботу.** Перегляньте `git diff`, зробіть commit (див. розділ 7). Потім — наступна фіча.

### Чому не варто просити «згенеруй весь застосунок»

- **Модель має обмежений контекст.** Чим більше коду за раз, тим більше вона «забуває» і суперечить сама собі.
- **Помилки накопичуються.** Одна хибна ідея на початку ламає все, що на ній збудовано, а знайти її у великій зміні важко.
- **Неможливо нормально перевірити.** 2000 рядків нового коду ви не прочитаєте й не зрозумієте; 100 рядків — легко.
- **Ви не вчитеся.** Мета — зрозуміти, як працює ваш застосунок, і вміти пояснити кожне рішення.

Маленькі кроки + перевірка після кожного = надійний результат.

### Приклади запитів

Запити можна писати українською або англійською. Чим конкретніше — тим краще.

**Обрати та уточнити ідею** (агент `plan`):

```text
Я хочу зробити застосунок для відстеження прочитаних книг. Запропонуй 3 варіанти MVP
різного розміру для навчального проєкту на 1–2 тижні. Для кожного — список user stories
і що краще залишити поза scope.
```

**Написати вимоги** (агент `build`, бо він змінює файл):

```text
Допоможи заповнити docs/requirements.md для мого застосунку "Книжкова полиця".
Спочатку постав мені 5–7 уточнювальних запитань і дочекайся відповідей.
Потім запиши вимоги за шаблоном у файлі. Не пиши код.
```

**Критично перевірити вимоги:**

```text
Прочитай docs/requirements.md. Які acceptance criteria нечіткі або неможливо перевірити тестом?
Чого не вистачає для MVP? Нічого не змінюй, лише перелічи проблеми.
```

**Спланувати фічу:**

```text
/plan-feature Користувач може додати книгу (назва — обов'язково, автор — необов'язково)
і бачить список усіх доданих книг. Дані поки зберігаються в пам'яті сервера.
```

**Уточнити план:**

```text
У плані замінимо окремий endpoint для пошуку на фільтрацію на frontend — книг буде мало.
Онови план і покажи лише змінені кроки.
```

**Реалізувати:**

```text
/implement
```

або крок за кроком:

```text
/implement Лише крок 1 плану: backend endpoint POST /api/books з валідацією і тестами.
```

**Перевірити:**

```text
/verify
```

**Зрозуміти код** (дуже рекомендовано після кожної фічі):

```text
Поясни, як працює додавання книги: від натискання кнопки до збереження на сервері.
Вкажи файли та функції, які беруть участь.
```

**Виправити помилку:**

```text
npm run test падає з такою помилкою: <вставте текст помилки>.
Знайди причину, поясни її і виправ. Потім запусти тести ще раз і покажи результат.
```

## 7. Робота з Git

### Рекомендований процес

1. **Працюйте в окремій гілці** для кожної фічі:
   ```bash
   git switch -c feature/add-books
   ```
2. **Робіть змістовні коміти** — кожен коміт = одна завершена, перевірена зміна. Перед комітом подивіться, що саме змінилося:
   ```bash
   git status
   ```
   ```bash
   git diff
   ```
   ```bash
   git add .
   ```
   ```bash
   git commit -m "Add endpoint for creating books"
   ```
3. **Відправте гілку у свій fork:**
   ```bash
   git push -u origin feature/add-books
   ```
4. **Створіть pull request у своєму fork.** На GitHub натисніть **Compare & pull request**. Обов'язково перевірте вгорі сторінки:
   - **base repository** — **ваш fork** (`<ваш-username>/opencode-playground`), а не оригінальний репозиторій (GitHub часто підставляє оригінальний за замовчуванням!);
   - **base** — `main`;
   - **compare** — ваша гілка (`feature/add-books`).
5. Перегляньте зміни в PR, за потреби виправте, потім зробіть **Merge**. Оновіть локальну гілку `main`:
   ```bash
   git switch main
   ```
   ```bash
   git pull
   ```

> Якщо основна гілка у вашому fork називається інакше (наприклад, `master`), використовуйте її назву замість `main`.

**Не відкривайте pull request в оригінальний навчальний репозиторій**, якщо викладач прямо цього не попросив.

### Хто відповідає за коміти

OpenCode може допомогти: показати зміни, запропонувати повідомлення коміту, підготувати опис PR. Але **ви** відповідаєте за те, що потрапляє в репозиторій: переглядайте `git diff` перед кожним комітом і розумійте кожну зміну. `git push` агентам заборонено конфігурацією — ця дія завжди за вами.

## 8. Вирішення проблем (Troubleshooting)

Більше технічних деталей — у [docs/development.md](docs/development.md#troubleshooting).

### Не встановлюються залежності (`npm install`)

- Перевірте `node --version` — потрібна **22.18+**. Встановіть актуальну LTS-версію.
- Запускайте команду з **кореня** репозиторію (там, де головний `package.json`).
- Спробуйте перевстановити з нуля (macOS/Linux/Git Bash):
  ```bash
  rm -rf node_modules apps/*/node_modules
  ```
  ```bash
  npm install
  ```
- Якщо ви в мережі університету/компанії з proxy — npm може потребувати налаштувань proxy.

### Frontend або backend не запускається

- Читайте вивід `npm run dev`: рядки з `[api]` стосуються backend, з `[web]` — frontend. Перша помилка зазвичай найважливіша.
- `Cannot find module ...` — виконайте `npm install`.
- Після зміни `vite.config.ts`, `package.json` або встановлення пакета — перезапустіть `npm run dev`.

### Порт уже зайнятий

Повідомлення `EADDRINUSE: address already in use :::3001` або `Port 5173 is already in use` означає, що порт використовує інша програма — часто це `npm run dev`, запущений в іншому терміналі, або інший проєкт.

- Закрийте інший процес (`Ctrl+C` у його терміналі). Знайти його: `lsof -i :3001` (macOS/Linux).
- Або запустіть на інших портах (ті самі змінні працюють і для `npm run test:e2e`):
  ```bash
  API_PORT=4001 WEB_PORT=5174 npm run dev
  ```
  PowerShell: `$env:API_PORT=4001; $env:WEB_PORT=5174; npm run dev`

### Frontend не може з'єднатися з backend («Cannot reach the API»)

- Переконайтеся, що backend працює: у терміналі є `[api] API server listening ...`, а [http://localhost:3001/api/version](http://localhost:3001/api/version) відкривається.
- Усі backend-маршрути мають починатися з `/api`, а frontend має використовувати відносні адреси (`fetch('/api/...')`), а не `http://localhost:3001/...`.
- Відкрийте DevTools браузера → вкладка **Network** і подивіться статус і відповідь запиту.

### Тести падають

- Прочитайте першу помилку: там є очікуване (`Expected`) і фактичне (`Received`) значення.
- Запускайте тести однієї частини: `npm run test -w apps/web` або `npm run test -w apps/api`.
- Playwright: `Executable doesn't exist` → `npm run test:e2e:install`. `Timed out waiting ... config.webServer` → сервер не стартував: запустіть `npm run dev` і подивіться помилку.
- Попросіть агента: «Ось помилка тесту: ... Поясни причину і виправ». Потім **самі** запустіть тести ще раз.

### OpenCode не має доступу до моделі

- Виконайте `/connect` і переконайтеся, що провайдер підключено; потім `/models` і оберіть модель.
- Помилка на кшталт `Model unavailable` — модель прибрали, вона недоступна у вашому регіоні або вимагає оплати. Оберіть іншу.
- Перевірте інтернет-з'єднання. `opencode --version` має показувати версію 2.x.
- Журнали OpenCode: `~/.local/share/opencode/log/opencode.log`.

### Безкоштовна модель досягла ліміту

- Зачекайте (ліміти часто денні) або оберіть іншу безкоштовну модель через `/models`.
- Економте запити: починайте нову сесію (`/new`) для нової задачі, давайте конкретні запити, не просіть агента перечитувати весь проєкт без потреби.

### AI-агент написав зламаний або неповний код

Це нормально — так буває. Що робити:

1. Запустіть перевірку (`/verify` або `npm run verify`) і покажіть агенту **конкретну** помилку.
2. Якщо зміна зовсім невдала — скасуйте її: `/undo` в OpenCode або `git restore .` (видаляє всі незакомічені зміни у відстежуваних файлах — будьте обережні; нові файли видаляє `git clean -fd`).
3. Зменште крок: попросіть реалізувати меншу частину.
4. Перевірте, чи вимоги в `docs/requirements.md` чіткі — розмиті вимоги дають розмитий код.
5. Почніть нову сесію (`/new`), якщо розмова стала довгою й агент плутається.
6. Спробуйте іншу модель.
7. Не приймайте фразу «все працює» без доказів: подивіться вивід команд і перевірте застосунок у браузері.

## 9. Чекліст готовності

Застосунок готовий до здачі, коли:

**Функціональність**
- [ ] Усі user stories з `docs/requirements.md` реалізовані.
- [ ] Кожен acceptance criterion перевірено вручну в браузері.
- [ ] Є стани завантаження, помилки та «порожньо», і вони коректно відображаються.
- [ ] Інтерфейс зручний на телефоні та на комп'ютері.

**Перевірки**
- [ ] `npm run lint` — без помилок.
- [ ] `npm run typecheck` — без помилок.
- [ ] `npm run test` — усі тести проходять, нові функції покриті тестами.
- [ ] `npm run build` — збірка успішна.
- [ ] `npm run test:e2e` — E2E тести проходять, головний сценарій покрито.

**Документація**
- [ ] `docs/requirements.md` описує те, що реально зроблено (включно зі scope).
- [ ] `docs/architecture.md` містить ключові рішення та актуальний список API endpoints.
- [ ] Немає секретів (паролів, ключів) у коді та історії Git.

**Розуміння**
- [ ] Ви можете пояснити, як дані проходять від інтерфейсу до backend і назад.
- [ ] Ви можете пояснити кожне архітектурне рішення і чому обрали саме його.
- [ ] Ви прочитали весь код, який додав агент, і розумієте його.
- [ ] Робота закомічена змістовними комітами, PR змерджено у вашому fork.

## 10. Довідка: команди та структура

### npm-команди (з кореня репозиторію)

| Команда | Що робить |
| --- | --- |
| `npm install` | встановити залежності обох застосунків |
| `npm run dev` | запустити backend (:3001) і frontend (:5173) разом |
| `npm run build` | зібрати обидва застосунки |
| `npm run lint` | перевірити код ESLint |
| `npm run typecheck` | перевірити типи TypeScript |
| `npm run test` | unit-тести (Vitest) обох застосунків |
| `npm run test:e2e` | end-to-end тести (Playwright) |
| `npm run test:e2e:install` | завантажити браузер для Playwright (один раз) |
| `npm run verify` | lint + typecheck + test + build однією командою |

Для одного застосунку додайте `-w apps/web` або `-w apps/api`, наприклад `npm run test -w apps/api`.

### Структура

```
.
├── apps/
│   ├── web/              React frontend (src/App.tsx — стартова сторінка)
│   └── api/              Express backend (src/server.ts — весь API)
├── e2e/                  Playwright тести
├── docs/
│   ├── requirements.md   вимоги до вашого застосунку
│   ├── architecture.md   архітектурні рішення
│   └── development.md    як запускати, тестувати, діагностувати
├── .opencode/
│   ├── agents/           субагенти frontend, backend, reviewer
│   └── commands/         /plan-feature, /implement, /verify
├── AGENTS.md             інструкції для AI-агентів
├── opencode.jsonc        конфігурація OpenCode
├── playwright.config.ts
└── package.json          npm workspaces і спільні скрипти
```
