### 2026-11-26 — Final accepted review decisions: one sequential E2E scenario, testable rows, missing-field messages, date/weight and body rules, UI labels

- **Context:** A strict review of `docs/architecture/` found remaining gaps that `/implement` would otherwise have to guess: two independent Playwright flows shared one store without flow ordering; duplicate-valued rows were not unambiguously targetable; missing-field error messages were incomplete for three fields; date and weight validation algorithms were underspecified; body-error precedence did not match the starter `express.json()` behavior; and some user-facing button labels were not fixed. The user accepted the following decisions.
- **Decision:**
  - **E2E:** replace the two independent flows with one sequential MVP scenario: fresh seed list → Fish category filter/statistics → add → edit → delete. During MVP implementation, replace the current starter `e2e/smoke.spec.ts` Welcome/version assertions with this scenario. Keep `workers: 1`, ports `3101`/`5174`, the isolated `DATA_DIR=test-results/angler-journal-e2e-data`, and the existing cleanup sequence unchanged. Steps run in this fixed order against one store, so no per-flow reset is needed.
  - **Row targeting:** rows have `data-testid="catch-record-<id>"` for tests only; the Catch record ID is never visually displayed. The Actions column stays after the six data columns. Accessible button names include an ordinal row number: `Edit <fishSpecies> caught on <caughtAt>, record <n>` and `Delete <fishSpecies> caught on <caughtAt>, record <n>`, substituting that record's values; `<n>` is the 1-based ordinal position of the row in the currently displayed (sorted and filtered) list.
  - **Missing-field messages:** a missing `fishCategory` uses `Fish category must be predatory or non-predatory`; a missing `fishCount` uses `Fish count must be an integer of at least 1`; a missing `totalWeightKg` uses `Total weight must be a number greater than 0`. No new “required” wording is introduced for these fields.
  - **Date validation:** require an exact `YYYY-MM-DD` string; parse numeric year/month/day; construct with `Date.UTC`; require the resulting UTC year/month/day to match the inputs; only then compare with the server's current UTC calendar date.
  - **Weight validation:** accept finite numbers only. “At most two decimal places” means the numeric value is within a small floating-point tolerance of a whole number of hundredths. Exponential JSON notation is accepted by numeric value, so `1e-2` is valid `0.01`.
  - **Body errors:** match existing `express.json()` behavior. Malformed JSON with a JSON `Content-Type` returns `400 { "field": "body", "message": "Invalid JSON" }`. Missing or non-JSON `Content-Type`, empty body, `null`, an array, or another non-object body returns `400 { "field": "body", "message": "Invalid request body" }`. Keep the existing full body-error precedence after that (unknown fields by ASCII-alphabetical first name, then missing fields, then known fields in the fixed field order).
  - **UI labels:** Add mode submit is `Add catch record`; Edit mode submit is `Save changes`; Cancel is `Cancel`. `Actions` is a generic UI term, not a domain glossary term, and is not added to `docs/glossary.md`.
  - **Build follow-up:** Build must later update `docs/development.md` with E2E ports `3101`/`5174` and the rule that Playwright never reuses running local servers. Architect does not edit that file.
- **Alternatives considered:** keeping two independent flows and relying on file order or a per-flow store reset (rejected: order was not guaranteed and extra fixtures add complexity); using species/date-only accessible names (rejected: duplicate-valued rows become ambiguous); inventing “Fish category is required” style messages (rejected: exact-message discipline); permissive `Date` parsing (rejected: invalid calendar dates roll over); string-based decimal counting that rejects `1e-2` (rejected: numeric value should decide); a custom raw-body parser that reports `Invalid JSON` without a JSON `Content-Type` (rejected: match `express.json()`); leaving submit/Cancel labels to the implementer or adding `Actions` to the glossary (rejected: exact-copy and glossary rules).
- **Consequences:** the single E2E scenario is deterministic and replaces the obsolete starter smoke assertions; duplicate rows are addressable in tests and by assistive technology; validation messages and algorithms are fully specified; this entry supersedes the earlier Flow A/Flow B wording and the earlier malformed-JSON precedence wording in the preceding entry; `docs/development.md` remains stale until Build applies the noted follow-up. No code, tests, data or non-architecture docs were changed by Architect.

### 2026-11-26 — Accepted architecture review follow-ups: E2E wiring, refetch failure, row actions, body precedence, display and delete-form rules

- **Context:** A strict review of `docs/architecture/` found eight remaining problems: the mandated E2E store isolation was not wired to the existing Playwright config and the two flows would race; the UI for a failed refetch after a successful mutation was undefined; Edit/Delete controls had no defined place or accessible names; request-body error precedence was only partly defined; duplicate records, date/category display, and form state after Delete were left to the implementer; and the claim that hosting was the only open choice was inaccurate. The user accepted the following decisions. The JSON safety choices and small backend module split remain intentional and unchanged.
- **Decision:**
  - **E2E architecture:** Playwright runs the API on port `3101` and the frontend on port `5174`. `workers` is `1`, and already-running local servers are never reused. The API receives `DATA_DIR=test-results/angler-journal-e2e-data`. Cleanup uses Node `fs` APIs only, in this exact sequence: `playwright.config.ts` removes the E2E data directory when the config is loaded, before the E2E web servers are spawned; Playwright global setup then removes it again idempotently (Playwright spawns web servers *before* global setup runs); global teardown removes it after the run. Flow A: fresh seed data → Fish category filter → expected statistics. Flow B: add → edit → delete a catch record.
  - **Refetch failure:** if a mutation succeeds but its follow-up `GET /api/catch-records` fails, show `Could not load catch records` with Retry, keep the last rendered list and Catch statistics visible, and never automatically repeat the successful mutation.
  - **Actions:** add an Actions column after the six data columns. Visible button labels are `Edit` and `Delete`. Accessible names are `Edit <fishSpecies> caught on <caughtAt>` and `Delete <fishSpecies> caught on <caughtAt>`, substituting that record's values.
  - **Body validation precedence:** (1) malformed JSON first; (2) then a missing/invalid `Content-Type`, empty body, `null`, array, or other non-object body as `Invalid request body`; (3) then unknown fields / `id`, choosing the ASCII-alphabetically first name if several are present; (4) then missing known fields; (5) then known-field validation in the existing fixed order `caughtAt`, `anglerName`, `fishCategory`, `fishSpecies`, `fishCount`, `totalWeightKg` (with the existing sub-rule for `totalWeightKg`).
  - **Data/UI:** only `id` is unique — duplicate catch records with identical editable values are allowed. Display Caught at exactly as `YYYY-MM-DD`. Display Fish category as `Predatory` or `Non-predatory`. If the deleted record is currently being edited, reset to empty Add mode; deleting another record preserves the current edit form.
  - **Retained safeguards:** keep the atomic temp-file rename, single in-process write queue, validation on read, JSON safety machinery, future Fishing Trips compatibility, and the small backend module split as intentional MVP choices; do not remove or simplify them.
- **Alternatives considered:** default ports 3001/5173 and reusing local dev servers (rejected: collisions and E2E would use the real `data/store.json`); relying on global setup alone for the pre-spawn cleanup (rejected: Playwright spawns web servers before global setup runs); parallel workers against one store (rejected: flow A's seed statistics race with flow B's mutations); silently retrying the successful mutation after a failed refetch (rejected: duplicate writes); leaving Edit/Delete placement and names to the implementer or adding them inside a data cell (rejected: E2E selectors and accessibility would be nondeterministic); returning the first unknown field by object key order (rejected: non-deterministic errors); raw API values or a formatted date in the list (rejected: contradicts the accepted display rules); clearing the form on every delete (rejected: discards an in-progress edit of another record); uniqueness across editable fields (rejected: requirements Story 2 requires duplicates to be stored); removing the JSON safeguards for simplicity (rejected again by the user).
- **Consequences:** E2E runs are isolated, serialized and repeatable; all previously open implementation guesses are closed; request errors and UI state transitions are deterministic; row actions are keyboard- and screen-reader-accessible. Hosting vendor/region remains the only open architectural choice.

### 2026-11-26 — Final review fixes: data pipeline, E2E isolation, normalization, UI details, request-body rules, retained safeguards

- **Context:** The accepted final-review findings closed the remaining ambiguities `/implement` would otherwise have to guess: statistics scope under a filter, E2E data isolation, whitespace normalization, filter/column/form/statistics UI details, the source of the species mapping, and request-body edge cases. The reviewer also challenged the JSON safety machinery as over-engineering; the user confirmed it is intentional for this MVP.
- **Decision:**
  - **Frontend data pipeline (exactly this order):** sort all loaded catch records by `caughtAt` descending, with `id` ascending for ties; apply the active Fish category filter; derive both the displayed list and Catch statistics from that filtered list. This refines the earlier "run on this sorted loaded list" wording.
  - **E2E strategy:** Playwright covers two important flows — (a) fresh seed data → filter → expected statistics, and (b) add → edit → delete a catch record. E2E runs use a separate temporary `DATA_DIR` and never the real `data/store.json`; the temporary directory is removed before and after each E2E run.
  - **Normalization:** trim `anglerName` and `fishSpecies` once, before validation. `POST` and `PUT` store and return the normalized values.
  - **UI rules:** the Fish category filter is a dropdown with All, Predatory, and Non-predatory; All is selected after reload and no filter persistence is required. The list columns are Caught at, Angler, Fish category, Fish species, Fish count, and Total weight. After successful Add or Edit, return to empty Add mode; Cancel Edit returns to Add mode without changing data. Catch statistics appear above the list, labeled `Total fish count` and `Total weight`. Both the list's Total weight values and the Catch statistics value use the same reusable one-decimal weight-format helper.
  - **Species validation source:** the exhaustive Fish species / Fish category mapping comes only from `docs/requirements.md` §6. `docs/glossary.md` is terminology and examples only, not a validation source.
  - **Request-body rules:** `POST`/`PUT` require a JSON object body. `null`, an array, or another non-object returns `400 { "field": "body", "message": "Invalid request body" }`. Malformed JSON returns `400 { "field": "body", "message": "Invalid JSON" }`. An `id` or any unknown field returns `400 { "field": "body", "message": "Unexpected field: <field name>" }`. Missing fields are validated in the already-decided fixed field order. Wrong types use these messages: `caughtAt` → `Caught at must be a valid date`; `anglerName` → `Angler must be a string`; `fishCategory` → `Fish category must be predatory or non-predatory`; `fishSpecies` → `Fish species must be a string`; `fishCount` → `Fish count must be an integer of at least 1`; `totalWeightKg` → `Total weight must be a number greater than 0`. For `totalWeightKg`, first validate a finite number greater than 0; only then validate at most two decimal places.
  - **Retained safeguards:** the small backend module split, atomic temp-file rename, single in-process write queue, validation on read, and future Fishing Trips compatibility are intentional MVP choices, not over-engineering; do not remove them.
  - **Build follow-up resolved:** the storage statement in `.opencode/agents/backend.md` is already correct; the earlier "must be fixed later by Build" note is complete and no action remains.
- **Alternatives considered:** computing statistics before filtering (rejected: contradicts user stories 4/5); running E2E against the real `data/store.json` or without store isolation (rejected: seed totals become non-deterministic); validating trimmed values but storing raw input (rejected: contradicts the requirements); a persisted or non-dropdown filter, showing IDs, leaving form state or statistics placement to the implementer (rejected: user-facing acceptance details); treating glossary examples as exhaustive or inventing another species source (rejected: ambiguity); leaving request-body edges to the implementer (rejected: non-deterministic error tests); removing the JSON safeguards for simplicity (rejected by the user as over-aggressive simplification).
- **Consequences:** statistics always match the active Fish category filter, E2E runs are repeatable and isolated, stored names/species contain no stray whitespace, request errors are deterministic, and the UI matches the agreed acceptance details. Hosting vendor/region remains the only open architectural choice.

### 2026-11-26 — Validation error precedence and isolated backend tests

- **Context:** These are the final two accepted implementation decisions from the architecture review; they close the remaining validation-precedence and test-isolation ambiguities without adding dependencies.
- **Decision:**
  - **Validation precedence:** if multiple editable fields are invalid in one request, validation returns only the first error in this fixed order: `caughtAt`, `anglerName`, `fishCategory`, `fishSpecies`, `fishCount`, `totalWeightKg`.
  - **Backend test isolation:** every backend test uses a separate temporary `DATA_DIR` and removes it after the test. The store module exposes a test-only reset helper that clears its initialization cache and write queue between tests. Tests never read or write the real `data/store.json`.
- **Alternatives considered:** returning all errors as an array or relying on request/object key order; sharing one temporary directory across tests; re-importing modules or deleting the real store to reset state; leaving the cached promise and write queue intact between tests.
- **Consequences:** API error responses are deterministic for multi-field mistakes, and tests cannot contaminate each other or production data. The reset helper is test-only and must not be called from production routes. Hosting vendor/region remains the only open architectural choice.

### 2026-11-26 — Explicit UI, validation, store, path, request, rounding, write and failure rules

- **Context:** The architecture review found accepted gaps that `/implement` would otherwise have to guess: sort/tie-break location, edit/delete UI mechanics, empty-state wording, browser validation hiding API errors, corrupt-store handling, store path resolution and initialization in tests, the exact request contract, rounding algorithm, write atomicity, and mutation failure UI. These rules refine (do not replace) the 2026-11-26 MVP API decision.
- **Decision:**
  - **Frontend sorting:** sort the loaded records by `caughtAt` descending; when dates are equal, sort by `id` ascending. The API does not promise an order. Refined on 2026-11-26 (see the final-review entry): apply the Fish category filter after sorting, then derive both the displayed list and Catch statistics from that filtered list.
  - **Single-screen UI mechanics:** one controlled form in Add mode or Edit mode. Selecting Edit sets the selected record and pre-fills all six editable fields. Delete uses `window.confirm`; only a confirmed deletion calls `DELETE`. When no filter is active and the loaded list is empty, show “No catch records yet”; when a category filter is active and has no matches, show “No records in this fish category”. Refined on 2026-11-26 (see the final-review entry): the filter is a dropdown with All selected after reload; Add/Edit/Cancel Edit return to empty Add mode.
  - **Client validation:** no browser validation that prevents submission. Forms use `noValidate` / no submission-blocking native `required` validation so the backend receives the request and returns the required inline API field error.
  - **Store failures:** validate the JSON store when it is read. If it is invalid or corrupt, catch-record API requests return the existing safe `500 { "message": "Internal server error" }` with no stack trace; the frontend load state shows “Could not load catch records” and Retry.
  - **Paths and initialization:** `seed.json` is resolved relative to `import.meta.url`. `DATA_DIR`, when set, is the directory for writable `store.json`; otherwise `store.json` uses the repository `data/` directory. Tests use a temporary `DATA_DIR`. `ensureStoreInitialized` is lazy, idempotent, and uses a cached promise before every catch-record route, so an imported Express app / Supertest also sees initialized data.
  - **Request contract:** `POST` and `PUT` require exactly six body fields: `caughtAt`, `anglerName`, `fishCategory`, `fishSpecies`, `fishCount`, `totalWeightKg`. `id` and unknown fields are rejected with `400` and `field: "body"`; malformed JSON is also `400` with `field: "body"`. Validation error field names are exactly `caughtAt`, `anglerName`, `fishCategory`, `fishSpecies`, `fishCount`, `totalWeightKg`; whole-body errors use `body`.
  - **Rounding and writes:** convert each allowed weight to integer hundredths before summing; calculate half-up to one decimal from that integer sum, then format as `X.Y kg`. All writes use a single in-process promise queue, write a temporary sibling file, then rename it to `store.json`.
  - **Mutation failure UI:** `400` shows the field message inline; `404` shows `Catch record not found`; `500`/network failures use the exact save/delete messages recorded on 2026-11-26. Keep the displayed list unchanged until a mutation succeeds; after success, refetch the full list.
- **Alternatives considered:** backend-side sorting/filtering/statistics; modal or separate edit page; native `required` validation with client-side blocking; trusting an existing store file without validation; cwd-relative store paths and startup-only initialization; permissive request bodies that ignore unknown fields; float summation with `toFixed`; in-place writes; optimistic updates.
- **Consequences:** Implementation is deterministic and testable without guessing UI mechanics, paths, or error field names. Supertest tests get seeded data via the lazy initializer. Stricter bodies and validated stores turn malformed input/corruption into consistent 400/500 JSON. Integer-hundredth arithmetic avoids floating-point rounding drift. The single-screen form and `noValidate` rule guarantee API messages reach the UI. No new dependencies are introduced.

### 2026-11-26 — MVP API, layering, frontend structure, validation, forms, errors, and reuse rules

- **Context:** MVP needs concrete, testable architecture for Angler Journal (catch records CRUD + filter/stats in UI) while staying minimal, aligned with `docs/requirements.md`/glossary, and compatible with planned Fishing Trips/Spots (`docs/features/fishing-trips-and-spots.md`).
- **Decision (recorded choices):**
  - **API (Catch records, MVP):** `GET /api/catch-records` returns all catch records. `POST /api/catch-records` creates a record and returns `201` with the created record. `PUT /api/catch-records/:id` replaces all six editable fields and returns `200` with the updated record. `DELETE /api/catch-records/:id` returns `204` with no body. No single-record `GET /api/catch-records/:id` and no separate stats endpoint in MVP. Filtering and statistics are computed in the frontend from fetched data; after a successful `POST`/`PUT`/`DELETE` the frontend refetches `GET /api/catch-records` (no optimistic updates).
  - **Backend layering (apps/api):** small modular split only — e.g. `src/routes/catchRecords.*`, `src/store.*`, `src/validation/catchRecords.*`, `src/types.ts`; `server.ts` composes app, middleware, routes, and starts only when run directly. No services/repositories layers added now.
  - **Frontend structure (apps/web/src):** use `src/components/`, `src/api.ts`, `src/types.ts`, and `src/utils/` only when a reusable helper is needed; no router. Keep API calls via relative `/api/...`.
  - **Validation:** backend hand-written validation is the source of truth. Frontend uses only light required-field UX, does not block submission with native validation (`noValidate`), and shows API inline field errors (API returns `{ "field": "<field name>", "message": "<human-readable explanation>" }` for `400`).
  - **Forms:** one controlled form with `useState`, in Add mode or Edit mode (see the 2026-11-26 UI refinement).
  - **Libraries/deps:** no new dependencies for MVP (existing stack only).
  - **Error format (non-400):** `404` returns `{ "message": "Catch record not found" }` (for missing catch record). Unexpected `500` returns `{ "message": "Internal server error" }`. No stack traces in responses. The `400` field-error shape from requirements is unchanged.
  - **Reuse rules:** extract a helper only when used in 2+ places or when it clearly isolates a tricky rule (e.g. date parsing/validation, trimming/normalization helpers, half-up rounding for total weight). Keep API/store/UI types in clear per-app locations (`apps/api/src/types.ts`, `apps/web/src/types.ts` or co-located in `api.ts`) without duplicating truth unnecessarily. No abstractions “for later”; prefer duplication over premature shared layers. **Frontend:** create one helper for calculating catch statistics and formatting total weight; do not duplicate that calculation across components.
- **Alternatives considered (summarized):** REST variants with `PATCH`/extra endpoints/stats endpoint; keeping backend mostly in `server.ts`; flatter frontend layout vs feature folders; validation libraries/forms libraries; broader error shapes (`field: null`, problem-details style); optimistic UI updates; adding new deps for convenience.
- **Consequences:** API is small and explicit (easy to test); frontend owns filtering/stats computation from the sorted loaded list after filtering (refined in the final-review entry; must follow same rounding/display rules as requirements). Backend split is clearer than one file but still minimal. No new deps reduces maintenance but means more manual validation/form code. Refetch-after-mutation is simpler than optimistic updates. Rules encourage a single stats/format helper in frontend to avoid drift.

### 2026-11-25 — Writable JSON store owned by the API

- **Context:** Catch records must survive server restarts so an angler can add, edit and delete them over a short deployment. The MVP has no accounts and the production app is one Node.js service.
- **Decision:** The API owns a writable JSON store at `data/store.json`. The frontend reads and changes catch records only through the API. For the MVP the store holds a `catchRecords` collection.
- **Refinement (2026-11-26):** `DATA_DIR`, when set, names the directory containing `store.json`; otherwise the repository `data/` directory is used. Writes go through a single in-process promise queue with a temporary sibling file and rename.
- **Alternatives:** An in-memory array (loses every edit on restart), SQLite or a hosted database (migrations and setup not justified for one small collection), browser `localStorage` (no shared API data and unreliable statistics).
- **Consequences:** No database dependency; writes must be atomic and serialized inside the single process; the directory containing the store must live on persistent storage. Adding a field to a record does not require a schema migration.

### 2026-11-25 — Seed data initializes the store once

- **Context:** `data/seed.json` supplies sample catch records for a fresh install, but edits made after startup must not be silently discarded.
- **Decision:** On first use, when `data/store.json` does not exist, the API reads `data/seed.json` and initializes the store from it once. When the store exists, it is loaded and validated before use (see the 2026-11-26 refinement). `data/seed.json` is immutable and is never written to by the application.
- **Refinement (2026-11-26):** initialization is lazy, idempotent, cached, and called before every catch-record route (not only process startup), so an imported Express app / Supertest sees initialized data. `data/seed.json` is resolved relative to `import.meta.url`. An existing store is validated on read; corrupt data returns the safe `500` JSON error instead of being used as-is.
- **Alternatives:** Re-seeding on every boot (erases stored edits), importing the seed at compile time (the API build has `rootDir: "src"`, so a file outside `src` cannot be imported into `dist`).
- **Consequences:** A fresh deployment starts with sample records; removing `data/store.json` resets the journal to the seed; the seed file remains a stable fixture for tests.

### 2026-11-25 — Stable persisted IDs for catch records

- **Context:** Editing and deleting must target one catch record, and the records in `data/seed.json` have no IDs.
- **Decision:** The API creates an ID for every catch record — both records initialized from seed data and records added later — and persists it in `data/store.json`. An assigned ID never changes, including after an edit. Refined on 2026-11-26: seed records receive `seed-1` through `seed-10` in seed-array order; new records use `crypto.randomUUID()`.
- **Alternatives:** Using array positions (break after deletion or reordering), deriving an ID from field values (break when those fields are edited).
- **Consequences:** A client can address a single record for edit and delete; IDs remain valid across restarts; every stored record carries its ID.

### 2026-11-25 — Persistent volume required, hosting vendor undecided

- **Context:** `store.json` must survive restarts and redeploys. The starter already runs as one Node.js web service that serves the built frontend and the API on one port.
- **Decision:** No hosting vendor or region is selected now. Any chosen platform must provide a persistent disk/volume for the directory containing `store.json` (`DATA_DIR` when set, otherwise the repository `data/` directory) and run the application with `npm run build` followed by `npm start`.
- **Alternatives:** Ephemeral free-tier hosts (the store would be wiped on restart), serverless platforms (require restructuring the long-running Express service and moving storage off disk).
- **Consequences:** Platform choice is narrowed but left open; deployment must include `data/` so seed initialization can work; the same setup runs locally and on the chosen host.

### 2026-11-25 — Fishing trips remain future work

- **Context:** `docs/features/fishing-trips-and-spots.md` plans a Fishing Trip entity and catch records assigned to trips, but the feature is explicitly out of MVP scope.
- **Decision:** The store design allows a later `fishingTrips` collection and an optional `tripId` on a catch record. Fishing trips, fishing spots, and trip assignment are not implemented in the MVP.
- **Alternatives:** Building the relationship now (adds unrequested work to the MVP), using a fixed record shape that cannot accept new fields (would require rewriting stored data later).
- **Consequences:** Adding the collection and optional field later does not invalidate existing catch records; current catch records are unassigned to any trip; API and UI work for trips stays a separate task.
